## Introduction aux bases de donnees Django

Dans ce chapitre d'introduction, nous explorons le module ORM de Django, qui permet de manipuler les donnees de maniere declarative. L'ORM (Object-Relational Mapping) est le cœur de la persistance dans Django, permettant de mapper nos modèles Python aux tables relationnelles de notre base de données. Une requête Django pour sélectionner tous les articles d'une catégorie peut s'écrire en une seule ligne : `Article.objects.filter(categorie="technologie")`. Cette syntaxe élégante masque la complexité des requêtes SQL sous-jacentes, tout en offrant une puissance considérable. Les modèles Django sont des classes Python qui définissent la structure de nos données. Chaque modèle correspond à une table dans notre base de données, et les relations entre modèles sont gérées nativement par Django. Par exemple, un modèle `Article` peut avoir une relation `ForeignKey` vers un modèle `Auteur` pour lier chaque article à son auteur. Le système de migrations de Django garantit que nos modifications du schéma sont trackées et appliquées de manière reproductible. Chaque changement de modèle génère un fichier de migration qui décrit la modification à appliquer à la base de données. Ces migrations sont stockées dans le dossier `migrations` de chaque application et peuvent être appliquées avec `python manage.py migrate`.

## Chapitre 1 : Les fondamentaux des modèles Django

Les modèles Django sont le point de départ de toute application Django qui a besoin de persister des données. Un modèle est simplement une classe Python qui hérite de `models.Model` et qui définit la structure des données que votre application va manipuler. Chaque attribut de classe correspond à un champ de base de données, et Django se charge automatiquement de créer et de mettre à jour le schéma de la base de données en fonction de ces définitions.

### 1.1 Création de votre premier modèle

Commençons par un exemple simple. Imaginez que nous construisions un blog. Notre modèle Article pourrait ressembler à ceci :

```python
from django.db import models
from django.contrib.auth.models import User

class Article(models.Model):
    titre = models.CharField(max_length=200)
    contenu = models.TextField()
    auteur = models.ForeignKey(User, on_delete=models.CASCADE)
    date_creation = models.DateTimeField(auto_now_add=True)
    mise_a_jour = models.DateTimeField(auto_now=True)
    statut = models.CharField(max_length=20, choices=[
        ('brouillon', 'Brouillon'),
        ('publie', 'Publié'),
        ('archive', 'Archivé'),
    ], default='brouillon')
    
    class Meta:
        ordering = ['-date_creation']
        
    def __str__(self):
        return self.titre
```

Ce modèle définit une table `article` dans notre base de données avec les colonnes suivantes : `id` (créé automatiquement), `titre` (varchar 200), `contenu` (text), `auteur_id` (clé étrangère vers la table auth_user), `date_creation` (datetime), `mise_a_jour` (datetime), et `statut` (varchar 20).

### 1.2 Types de champs complets

Django propose une large variété de types de champs, chacun correspondant à un type de colonne SQL spécifique :

- `CharField` : Pour les chaînes de caractères de longueur limitée. Accepte le paramètre `max_length` qui est requis pour ce type de champ.
- `TextField` : Pour de plus grandes quantités de texte sans limite de longueur prédéfinie.
- `IntegerField` : Pour les nombres entiers.
- `BooleanField` : Pour les valeurs Vrai/Faux, stockées généralement sous forme de tinyint(1) dans MySQL ou de boolean dans PostgreSQL.
- `DateField` : Pour les dates, avec divers formats de représentation possibles.
- `DateTimeField` : Pour les dates et heures combinées.
- `TimeField` : Pour les heures seules.
- `FileField` : Pour gérer les fichiers téléchargés, nécessite le paramètre `upload_to` qui spécifie le répertoire de stockage.
- `ImageField` : Hérite de `FileField` et ajoute une validation pour s'assurer que le fichier est une image valide.
- `ForeignKey` : Pour créer une relation many-à-un. Il faut spécifier le modèle cible et le comportement de suppression (`on_delete`).
- `ManyToManyField` : Pour créer des relations many-à-many. Django crée automatiquement une table de liaison pour gérer la relation.
- `OneToOneField` : Pour créer une relation un-à-un, souvent utilisée pour étendre le modèle User de Django.

Chaque type de champ peut accepter de nombreux paramètres optionnels qui contrôlent le comportement de validation, le stockage dans la base de données et l'affichage dans les formulaires. Les paramètres les plus courants incluent `null` (permet la valeur NULL en base de données), `blank` (permet un champ vide dans les formulaires), `default` (valeur par défaut), et `choices` (liste de choix prédéfinis).

### 1.3 Options Meta et méthodes de modèle

La classe `Meta` intérieure permet de définir des options de comportement pour votre modèle :

```python
class Article(models.Model):
    titre = models.CharField(max_length=200)
    contenu = models.TextField()
    
    class Meta:
        verbose_name = "Article"
        verbose_name_plural = "Articles"
        ordering = ['-date_creation']
        get_latest_by = 'date_creation'
        unique_together = ['titre', 'auteur']
```

Les options les plus utiles incluent :
- `ordering` : Définit l'ordre par défaut des requêtes queryset.
- `verbose_name` et `verbose_name_plural` : Noms humains pour le modèle dans l'admin Django.
- `db_table` : Nom personnalisé pour la table de base de données.
- `managed` : Si False, Django ne gère pas les migrations pour ce modèle.
- `abstract` : Si True, ce modèle sera abstrait et ne créera pas de table.

En plus de la classe `Meta`, vous pouvez définir des méthodes sur vos modèles pour encapsuler la logique métier :

```python
class Article(models.Model):
    titre = models.CharField(max_length=200)
    statut = models.CharField(max_length=20, default='brouillon')
    
    def publier(self):
        """Publier l'article"""
        self.statut = 'publie'
        self.save()
    
    @property
    def est_publie(self):
        """Propriété indiquant si l'article est publié"""
        return self.statut == 'publie'
    
    @classmethod
    def get_publies(cls):
        """Méthode de classe pour récupérer les articles publiés"""
        return cls.objects.filter(statut='publie')
    
    def commentaires_count(self):
        """Compter le nombre de commentaires"""
        return self.commentaires.count()
```

Ces méthodes rendent votre code plus orienté objet et facilitent la réutilisation de la logique à travers votre application.

## Chapitre 2 : Requêtes ORM avancées

Maintenant que nous avons des modèles, explorons comment les interroger efficacement. L'ORM Django offre une syntaxe riche et expressive pour construire des requêtes complexes.

### 2.1 Filtres de base et lookups

La méthode `filter()` accepte de nombreux paramètres de lookup qui se traduisent en clauses SQL :

```python
# Exact match
Articles.objects.filter(titre='Mon Titre')

# Contains (SQL LIKE %...)
Articles.objects.filter(titre__contains='Django')

# Start with
Articles.objects.filter(titre__startswith='D')

# Exact date match
from datetime import date
Articles.objects.filter(date_creation__date=date(2024, 1, 1))

# Greater than
Articles.objects.filter(prix__gt=50)

# Less than or equal
Articles.objects.filter(prix__lte=100)

# In list
Articles.objects.filter(id__in=[1, 2, 3, 4, 5])
```

Les lookups peuvent être chaînés pour créer des requêtes AND :

```python
# SQL equivalent: SELECT * FROM article WHERE categorie='tech' AND statut='publie'
Articles.objects.filter(categorie='tech').filter(statut='publie')

# Ou avec la syntaxe raccourcie
Articles.objects.filter(categorie='tech', statut='publie')
```

### 2.2 Q objects pour des requêtes complexes

Parfois, nous avons besoin de créer des requêtes OR (disjonction) qui ne peuvent pas être exprimées simplement en enchaînant des `filter()`. C'est ici qu'interviennent les `Q objects` :

```python
from django.db.models import Q

# SQL equivalent: SELECT * FROM article WHERE categorie='tech' OR statut='publie'
articles = Articles.objects.filter(
    Q(categorie='tech') | Q(statut='publie')
)

# On peut aussi faire de la négation
articles = Articles.objects.filter(
    ~Q(statut='brouillon')
)

# Combinaison AND et OR
articles = Articles.objects.filter(
    Q(categorie='tech') & ~Q(auteur__isnull=True)
)
```

Les `Q objects` sont particulièrement utiles pour construire des formulaires de recherche dynamiques où les conditions peuvent varier selon les entrées de l'utilisateur.

### 2.3 Agrégations et annotations

Le module `django.db.models` propose des fonctions d'agrégation puissantes qui vous permettent de calculer des statistiques directement dans la base de données :

```python
from django.db.models import Count, Avg, Sum, Min, Max

# Nombre total d'articles
total = Article.objects.count()

# Nombre d'articles par auteur
nombre_par_auteur = Auteur.objects.annotate(
    nombre_articles=Count('article')
).order_by('-nombre_articles')

# Moyenne du prix des produits
statistiques = Produit.objects.aggregate(
    moyenne_prix=Avg('prix'),
    prix_min=Min('prix'),
    prix_max=Max('prix'),
    nombre_total=Count('id')
)
```

L'`annotate()` ajoute des champs au queryset résultant, tandis que `aggregate()` renvoie un dictionnaire avec les valeurs calculées. C'est extrêmement utile pour créer des tableaux de bord, des rapports, et des vues statistiques.

### 2.4 Jointures efficaces : select_related et prefetch_related

L'un des problèmes les plus courants en Django est le "problème N+1", où Django exécute une requête principale plus une requête par objet lié. Pour y remédier :

```python
# Mauvais : provoque N+1 requêtes pour les auteurs
articles = Article.objects.all()
for article in articles:
    print(article.auteur.nom)  # N requêtes supplémentaires

# Bon : une seule requête avec jointure
articles_optimisees = Article.objects.select_related('auteur').all()
for article in articles_optimisees:
    print(article.auteur.nom)  # Aucune requête supplémentaire
```

- `select_related()` effectue une jointure SQL INNER JOIN et est optimal pour les relations ForeignKey et OneToOneField.
- `prefetch_related()` exécute deux requêtes séparées et fait la mise en mémoire cache des résultats dans Python, ce qui est optimal pour les relations ManyToMany et les relations inverses.

```python
# Pour ManyToMany
articles_avec_tags = Article.objects.prefetch_related('tags').all()
for article in articles_avec_tags:
    for tag in article.tags.all():
        # Pas de requête SQL supplémentaire ici
        pass
```

Ces optimisations peuvent avoir un impact significatif sur les performances, surtout avec de grandes quantités de données.

## Chapitre 3 : Formulaires ModelForm et validation

Django rend la création de formulaires à partir de modèles extrêmement simple grâce à `ModelForm`. Cela permet de générer automatiquement des formulaires à partir de vos modèles, avec une validation intégrée qui correspond aux définitions de vos champs de modèle.

### 3.1 Création basique de ModelForm

```python
from django import forms
from .models import Article

class ArticleForm(forms.ModelForm):
    class Meta:
        model = Article
        fields = ['titre', 'contenu', 'categorie', 'auteur']
        widgets = {
            'titre': forms.TextInput(attrs={'class': 'form-control', 'maxlength': 200}),
            'contenu': forms.Textarea(attrs={'class': 'form-control', 'rows': 10}),
            'categorie': forms.Select(attrs={'class': 'form-control'}),
        }
        labels = {
            'titre': 'Titre de l\'article',
            'contenu': 'Contenu de l\'article',
            'categorie': 'Catégorie',
        }
        help_texts = {
            'titre': 'Maximum 200 caractères',
            'contenu': 'Rédigez votre article ici',
        }
```

### 3.2 Personnalisation du nettoyage des données

Vous pouvez ajouter des méthodes de nettoyage personnalisées pour valider des champs spécifiques ou effectuer une validation croisée entre champs :

```python
class ArticleForm(forms.ModelForm):
    class Meta:
        model = Article
        fields = ['titre', 'contenu', 'statut']
    
    def clean_titre(self):
        """Validation personnalisée pour le champ titre"""
        titre = self.cleaned_data['titre']
        if len(titre) > 200:
            raise forms.ValidationError("Le titre ne peut pas dépasser 200 caractères")
        if len(titre) < 5:
            raise forms.ValidationError("Le titre doit contenir au moins 5 caractères")
        return titre
    
    def clean(self):
        """Validation croisée des champs"""
        cleaned_data = super().clean()
        titre = cleaned_data.get('titre')
        contenu = cleaned_data.get('contenu')
        
        # Si le contenu est fourni, le titre l'est aussi
        if contenu and not titre:
            raise forms.ValidationError(
                "Si vous fournissez du contenu, un titre est requis"
            )
        return cleaned_data
```

### 3.3 Gestion des formulaires dans les vues

Dans vos vues, la gestion des formulaires suit un pattern bien défini :

```python
from django.shortcuts import render, redirect, get_object_or_404
from django.contrib.auth.decorators import login_required
from .forms import ArticleForm
from .models import Article

@login_required
def article_create(request):
    """Vue pour créer un nouvel article"""
    if request.method == 'POST':
        form = ArticleForm(request.POST, request.FILES)
        if form.is_valid():
            article = form.save(commit=False)
            article.auteur = request.user
            article.save()
            # Message de succès
            from django.contrib import messages
            messages.success(request, 'Article créé avec succès!')
            return redirect('article_detail', pk=article.pk)
    else:
        form = ArticleForm()
    
    return render(request, 'articles/create.html', {'form': form})

@login_required
def article_update(request, pk):
    """Vue pour modifier un article existant"""
    article = get_object_or_404(Article, pk=pk)
    if article.auteur != request.user:
        from django.http import HttpResponseForbidden
        return HttpResponseForbidden("Vous n'êtes pas autorisé à modifier cet article")
    
    if request.method == 'POST':
        form = ArticleForm(request.POST, request.FILES, instance=article)
        if form.is_valid():
            form.save()
            from django.contrib import messages
            messages.success(request, 'Article mis à jour avec succès!')
            return redirect('article_detail', pk=article.pk)
    else:
        form = ArticleForm(instance=article)
    
    return render(request, 'articles/form.html', {'form': form})

@login_required
def article_delete(request, pk):
    """Vue pour supprimer un article"""
    article = get_object_or_404(Article, pk=pk)
    if article.auteur != request.user:
        return HttpResponseForbidden("Vous n'êtes pas autorisé à supprimer cet article")
    
    if request.method == 'POST':
        article.delete()
        from django.contrib import messages
        messages.success(request, 'Article supprimé avec succès!')
        return redirect('article_list')
    
    return render(request, 'articles/confirm_delete.html', {'article': article})
```

## Chapitre 4 : Vues basées sur les classes (CBV)

Bien que les fonctions views soient parfaitement viables, Django propose des vues basées sur des classes (CBV) qui réduisent considérablement la quantité de code boilerplate requis pour les opérations CRUD courantes.

### 4.1 Vue ListView

```python
from django.views.generic import ListView
from .models import Article

class ArticleListView(ListView):
    model = Article
    template_name = 'articles/list.html'
    context_object_name = 'articles'
    paginate_by = 10
    ordering = ['-date_creation']
    allow_empty = True
    
    def get_context_data(self, kwargs):
        """Ajouter des données supplémentaires au contexte"""
        context = super().get_context_data(kwargs)
        context['total_articles'] = Article.objects.count()
        return context
```

### 4.2 Vue DetailView

```python
from django.views.generic import DetailView

class ArticleDetailView(DetailView):
    model = Article
    template_name = 'articles/detail.html'
    context_object_name = 'article'
    
    def get_context_data(self, kwargs):
        context = super().get_context_data(kwargs)
        # Ajouter des données supplémentaires
        context['commentaires'] = self.object.commentaires.all()[:5]
        return context
```

### 4.3 Vue CreateView

```python
from django.views.generic import CreateView
from .forms import ArticleForm
from django.contrib.messages.views import SuccessMessageMixin

class ArticleCreateView(SuccessMessageMixin, CreateView):
    model = Article
    form_class = ArticleForm
    template_name = 'articles/form.html'
    success_url = '/articles/'
    success_message = "Article créé avec succès!"
```

### 4.4 Vue UpdateView et DeleteView

```python
from django.views.generic import UpdateView, DeleteView
from django.urls import reverse_lazy

class ArticleUpdateView(UpdateView):
    model = Article
    form_class = ArticleForm
    template_name = 'articles/form.html'
    success_url = reverse_lazy('article_list')

class ArticleDeleteView(DeleteView):
    model = Article
    template_name = 'articles/confirm_delete.html'
    success_url = reverse_lazy('article_list')
    success_message = "Article supprimé avec succès!"
    
    def delete(self, request, *args, kwargs):
        messages.success(request, self.success_message)
        return super().delete(request, *args, kwargs)
```

### 4.5 Avantages et inconvénients des CBV

Les vues basées sur les classes offrent plusieurs avantages :
- Réduction du code répétitif (boilerplate)
- Structure cohérente à travers l'application
- Mixins réutilisables pour la composition de fonctionnalité
- Testabilité accrue grâce à des méthodes clairement définies

Les inconvénients incluent :
- Courbe d'apprentissage plus raide pour les débutants
- Personnalisation excessive peut devenir complexe
- Debuggage peut être plus difficile pour les novices

Le choix entre vues fonctionnelles et basées sur classes dépend souvent du projet, de l'équipe et des exigences spécifiques.

## Chapitre 5 : Fichiers statiques et media

La gestion des fichiers statiques et des médias est un aspect crucial du développement web Django.

### 5.1 Configuration settings.py

Dans votre fichier `settings.py`, la configuration suivante est essentielle :

```python
# URL de base pour accéder aux fichiers statiques via web
STATIC_URL = '/static/'

# Répertoires supplémentaires où Django cherchera les fichiers statiques
STATICFILES_DIRS = [
    BASE_DIR / "static",
    BASE_DIR / "assets",
]

# Paramètres des médias (fichiers utilisateurs)
MEDIA_URL = '/media/'
MEDIA_ROOT = BASE_DIR / "media"

# Désactiver le mode debug en production
DEBUG = False

# Key secrète pour la sécurité cryptographique
SECRET_KEY = 'votre-cle-secrete-ici'
```

### 5.2 Fichiers statiques dans les templates

Pour utiliser les fichiers statiques dans vos templates, chargez d'abord le tag library :

```html
{% load static %}

<!-- Feuille de style CSS -->
<link rel="stylesheet" href="{% static 'css/style.css' %}">

<!-- Script JavaScript -->
<script src="{% static 'js/main.js' %}"></script>

<!-- Icône favicon -->
<link rel="shortcut icon" href="{% static 'images/favicon.ico' %}">
```

## Chapitre 6 : Sécurité et bonnes pratiques

La sécurité est primordiale dans le développement web, et Django offre de nombreuses protections intégrées.

### 6.1 Protection contre les injections SQL

Django utilise systématiquement des requêtes paramétrées dans son ORM, ce qui signifie que les valeurs des utilisateurs sont toujours traitées comme des données, jamais comme du code SQL exécutable. Par exemple :

```python
# Sûr : Django paramètre cette requête
Article.objects.filter(titre=request.GET.get('titre'))

# Dangereux : concaténation directe de SQL
# NE JAMAIS faire ceci :
# Article.objects.raw(f"SELECT * FROM article WHERE titre = '{request.GET.get('titre')}'"")
```

Cependant, soyez toujours vigilant et n'utilisez jamais de concaténation de chaînes SQL directe, même si Django se protège contre la plupart des attaques par injection.

### 6.2 Validation des entrées

Utilisez toujours des formulaires Django pour valider les entrées utilisateur. Les validateurs intégrés incluent :

```python
from django import forms
from django.core.validators import validate_email, RegexValidator

class ContactForm(forms.Form):
    email = forms.EmailField(label='E-mail', validators=[validate_email])
    telephone = forms.CharField(
        label='Téléphone',
        validators=[RegexValidator(r'^\d{10}$', 'Format de téléphone invalide')
    ]
    age = forms.IntegerField(min_value=18, max_value=99)
```

Les champs `EmailField` et `CharField` avec `validators` assurent que les données respectent vos exigences avant d'être traitées ou enregistrées.

### 6.3 Headers de sécurité Django

Configurez ces settings cruciaux dans votre `settings.py` de production :

```python
# Protection contre les attaques XSS
SECURE_BROWSER_XSS_FILTER = True

# Empêcher les essais de détermination de type de contenu
SECURE_CONTENT_TYPE_NOSNIFF = True

# Politique de sécurité des temps HTTP (HSTS)
SECURE_HSTS_INCLUDE_SUBDOMAINS = True
SECURE_HSTS_SECONDS = 31536000  # 1 an en secondes
SECURE_HSTS_PRELOAD = True

# Redirection HTTPS
SECURE_SSL_REDIRECT = True

# Interdiction du framing (clickjacking protection)
X_FRAME_OPTIONS = 'DENY'

# Rediriger automatiquement HTTP vers HTTPS
SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')
```

Ces settings protègent vos utilisateurs contre diverses attaques courantes notamment le cross-site scripting (XSS), le clickjacking, et les downgrades d'attaque HTTPS.

### 6.4 Gestion des mots de passe

Django gère le hachage des mots de passe par défaut de manière sécurisée :

```python
from django.contrib.auth.hashers import make_password, check_password

# Hacher un mot de passe
mot_de_passe_hache = make_password('password123')

# Vérifier un mot de passe
if check_password('password123', mot_de_passe_hache):
    print("Mot de passe correct!")
```

Le système d'authentification de Django utilise PBKDF2 par défaut, qui est lent intentionnellement pour résister aux attaques par force brute. Vous pouvez configurer l'algorithme de hachage dans les settings.

### 6.5 Protection CSRF

Django inclut une protection CSRF (Cross-Site Request Forgery) par défaut :

```python
# Dans vos templates de formulaire
{% csrf_token %}

# Dans vos vues, assurez-vous que CsrfViewMiddleware est activé
# dans MIDDLEWARE dans settings.py
```

La balise `{% csrf_token %}` insère un champ caché unique dans chaque formulaire qui valide que la requête provient de votre site et non d'un tiers malveillant.

## Chapitre 8 : Personnalisation avancée

### 8.1 Gestionnaires de modèles personnalisés

Les gestionnaires (managers) vous permettent de personnaliser les requêtes par défaut pour vos modèles :

```python
from django.db import models

class PublishedManager(models.Manager):
    """Gestionnaire qui ne retourne que les articles publiés"""
    
    def get_queryset(self):
        return super().get_queryset().filter(statut='publie')
    
    def recents(self, days=7):
        """Retourne les articles des N derniers jours"""
        from django.utils import timezone
        from datetime import timedelta
        return self.get_queryset().filter(
            date_publication__gte=timezone.now() - timedelta(days=days)
        )

class Article(models.Model):
    titre = models.CharField(max_length=200)
    statut = models.CharField(max_length=20, default='brouillon')
    date_publication = models.DateTimeField()
    
    # Gestionnaire par défaut (tous les articles)
    objects = models.Manager()
    
    # Gestionnaire personnalisé (articles publiés)
    published = PublishedManager()
    
    @staticmethod
    def get_publies_recents(days=7):
        """Méthode pratique combinant les deux gestionnaires"""
        return Article.published.recents(days)
```

Vous pouvez avoir plusieurs gestionnaires par modèle, ce qui est utile pour encapsuler différentes vues de vos données.

### 8.2 Signaux Django

Les signaux permettent d'exécuter du code en réponse à des événements du modèle :

```python
from django.db.models.signals import post_save, post_delete
from django.dispatch import receiver
from .models import Article

@receiver(post_save, sender=Article)
def article_saved(sender, instance, created, kwargs):
    if created:
        # Envoyer une notification, mettre à jour des caches, etc.
        print(f"Nouvel article créé : {instance.titre}")

@receiver(post_delete, sender=Article)
def article_deleted(sender, instance, kwargs):
    # Nettoyer les ressources associées
    print(f"Article supprimé : {instance.titre}")

# Connecter le signal manuellement
post_save.connect(article_saved, sender=Article)

# Ou utiliser le décorateur @receiver comme montré ci-dessus
```

Les signaux sont utiles pour :
- Envoyer des emails à la création d'un objet
- Mettre à jour des caches ou des compteurs
- Nettoyer des fichiers associés à la suppression
- Loguer des actions importantes

### 8.3 Personnalisation de l'admin Django

Le panneau d'administration de Django est par défaut très puissant, mais peut être personnalisé :

```python
from django.contrib import admin
from .models import Article, Auteur

# Enregistrement de base
admin.site.register(Article)

# Personnalisation de l'interface d'administration
@admin.register(Article)
class ArticleAdmin(admin.ModelAdmin):
    list_display = ('titre', 'auteur', 'statut', 'date_creation')
    list_filter = ('statut', 'date_creation')
    search_fields = ('titre', 'contenu')
    date_hierarchy = 'date_creation'
    prepopulated_fields = {'slug': ('titre',)}
    raw_id_fields = ('auteur',)
    
    # Personnalisation des champs du formulaire
    fieldsets = (
        (None, {'fields': ('titre', 'contenu')}),
        ('Statut et date', {'fields': ('statut', 'date_publication'), 'classes': ('collapse',)}),
    )
    
    # Actions personnalisées
    actions = ['publier_action', 'archiver_action']
    
    def publier_action(self, request, queryset):
        """Action admin pour publier plusieurs articles"""
        updated = queryset.update(statut='publie')
        self.message_user(request, f'{updated} article(s) publié(s).')
    publier_action.short_description = "Publier les articles sélectionnés"
    
    def archiver_action(self, request, queryset):
        """Action admin pour archiver plusieurs articles"""
        updated = queryset.update(statut='archive')
        self.message_user(request, f'{updated} article(s) archivé(s).')
    archiver_action.short_description = "Archiver les articles sélectionnés"
```

### 8.4 Middleware personnalisé

Le middleware permet de traiter les requêtes et réponses globalement :

```python
class LoggingMiddleware:
    """Middleware de journalisation simple"""
    
    def __init__(self, get_response):
        self.get_response = get_response
    
    def __call__(self, request):
        # Code s'exécute avant la vue
        response = self.get_response(request)
        
        # Code s'exécute après la vue
        # Logger la requête
        if request.user.is_authenticated:
            print(f"Utilisateur {request.user} a accédé à {request.path}")
        
        return response
```

Enregistrez-le dans `MIDDLEWARE` dans `settings.py` :

```python
MIDDLEWARE = [

    'django.contrib.sessions.middleware.SessionMiddleware',
    'django.middleware.common.CommonMiddleware',
    'django.middleware.csrf.CsrfViewMiddleware',
    'django.contrib.auth.middleware.AuthenticationMiddleware',
    'django.contrib.messages.middleware.MessageMiddleware',
    'django.middleware.clickjacking.XFrameOptionsMiddleware',

]
```

### 9.1 Structure des tests Django

```python
from django.test import TestCase, Client, RequestFactory
from django.urls import reverse
from .models import Article, Auteur

class ArticleModelTest(TestCase):
    """Tests unitaires pour le modèle Article"""
    
    def setUp(self):
        """Configuration exécutée avant chaque test"""
        self.auteur = Auteur.objects.create(
            nom="Jean Dupont",
            email="jean@example.com"
        )

            titre="Article de test",

        self.assertEqual(self.article.titre, "Article de test")
        self.assertEqual(self.article.auteur, self.auteur)
        self.assertEqual(self.article.statut, 'publie')
    
    def test_str_representation(self):
        """Tester la représentation en chaîne de caractères"""
        self.assert str__(self.article) == "Article de test"
    
    def test_article_avec_auteur(self):
        """Tester la relation avec l'auteur"""
        articles = Article.objects.filter(auteur=self.auteur)
        self.assertEqual(articles.count(), 1)
        self.assertEqual(articles.first(), self.article)
    
    def test_article_publie(self):
        """Tester que seuls les articles publiés sont récupérables"""
        # Créer un article en brouillon
        Article.objects.create(
            titre="Brouillon",
            contenu="Contenu en brouillon",
            auteur=self.auteur,
            statut='brouillon'
        )
        # Vérifier que seulement l'article publié apparaît
        publies = Article.objects.filter(statut='publie')
        self.assertEqual(publies.count(), 1)
    
    def test_ordre_par_defaut(self):
        """Tester l'ordre par défaut des articles"""
        # Créer plusieurs articles avec différentes dates
        Article.objects.create(
            titre="Article récent",
            contenu="Contenu récent",
            auteur=self.auteur,
            date_publication="2024-01-15",
            statut='publie'
        )
        # Récupérer et vérifier l'ordre
        articles = Article.objects.all()
        self.assertEqual(articles.first().titre, "Article récent")
```

```python
class IntegrationTest(TestCase):
    """Tests d'intégration complets"""

        self.client = Client()
        self.auteur = Auteur.objects.create(nom="Intégration Test")
        self.article = Article.objects.create(

    def test_cycle_complet_creation_lecture_suppression(self):
        """Tester le cycle complet création -> lecture -> suppression"""
        # 1. Créer un article via le formulaire
        response = self.client.post(
            reverse('article_create'),
            {
                'titre': 'Article cycle',
                'contenu': 'Contenu du cycle',
            },
            follow=True
        )
        self.assertEqual(response.status_code, 200)
        
        # 2. Vérifier que l'article apparaît dans la liste
        response = self.client.get(reverse('article_list'))
        self.assertContains(response, 'Article cycle')
        
        # 3. Vérifier la page de détail
        response = self.client.get(
            reverse('article_detail', args=[self.article.pk])
        )
        self.assertContains(response, 'Article cycle')
        
        # 4. Supprimer l'article
        response = self.client.post(
            reverse('article_delete', args=[self.article.pk]),
            follow=True
        )
        self.assertContains(response, 'été supprimé')
        
        # 5. Vérifier qu'il n'apparaît plus
        response = self.client.get(reverse('article_list'))
        self.assertNotContains(response, 'Article cycle')
```

### 10.1 Configuration CI/CD avec GitHub Actions

Configurons un pipeline d'intégration continue :

```yaml
# .github/workflows/python.yml
name: CI/CD Pipeline

on:
    push:
        branches: [ main, develop ]
    pull_request:
        branches: [ main ]

jobs:
    test:
        runs-on: ubuntu-latest
        steps:
            - uses: actions/checkout@v3
            
            - name: Set up Python
              uses: actions/setup-python@v4
              with:
                  python-version: '3.11'
            
            - name: Install dependencies
              run: |
                  python -m pip install --upgrade pip
                  pip install -r requirements.txt
                  pip install pytest django pytest-django
            
            - name: Run tests
              run: |
                  python -m pytest
            
            - name: Lint with flake8
              run: |
                  pip install flake8
                  flake8 . --count --select=E9,F63,F7,F82 --show-source --statistics
            
            - name: Check code style with black
              run: |
                  pip install black
                  black . --check
    
    deploy:
        needs: test
        runs-on: ubuntu-latest
        if: github.ref == 'refs/heads/main'
        steps:
            - uses: actions/checkout@v3
            
            - name: Deploy to server
              env:
                  SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
                  DEPLOY_USER: ${{ secrets.DEPLOY_USER }}
              run: |
                  echo "$SSH_PRIVATE_KEY" | tr -d '\n' | ssh-add - > /dev/null 2>&1
```

```python
def health_check(request):
```

- Utiliser des requêtes N+1 sans optimisation via `select_related` ou `prefetch_related`

- Oublier de définir `on_delete` pour les relations ForeignKey ou ManyToMany
- Négliger de tester les vues et les formulaires avec le framework de tests Django inclus
- Stocker des informations sensibles en dur dans le code source ou les settings
- Oublier d'appliquer `python manage.py migrate` après avoir créé de nouvelles migrations

```python
# models.py
from django.db import models
from django.contrib.auth.models import User
from django.urls import reverse

class Categorie(models.Model):
    nom = models.CharField(max_length=100)
    slug = models.SlugField(max_length=100, unique=True)
    
    class Meta:
        ordering = ['nom']
    
    def __str__(self):
        return self.nom

class Tag(models.Model):
    nom = models.CharField(max_length=50, unique=True)
    
    def __str__(self):
        return self.nom

class Article(models.Model):
    titre = models.CharField(max_length=200)
    slug = models.SlugField(max_length=200, unique=True)
    auteur = models.ForeignKey(User, on_delete=models.CASCADE)
    categorie = models.ForeignKey(Categorie, on_delete=models.SET_NULL, null=True)
    tags = models.ManyToManyField(Tag, blank=True)
    contenu = models.TextField()
    date_creation = models.DateTimeField(auto_now_add=True)
    mise_a_jour = models.DateTimeField(auto_now=True)
    statut = models.CharField(max_length=20, choices=[
        ('brouillon', 'Brouillon'),
        ('publie', 'Publié'),
        ('archive', 'Archivé'),
    ], default='brouillon')
    
    class Meta:
        ordering = ['-date_creation']
        indexes = [
            models.Index(fields=['-date_creation']),
            models.Index(fields=['statut']),
        ]
    
    def __str__(self):
        return self.titre
    
    def get_absolute_url(self):
        return reverse('article_detail', args=[str(self.id), self.slug])
    
    @property
    def est_publie(self):
        return self.statut == 'publie'
    
    def nombre_commentaires(self):
        return self.commentaires.count()

class Commentaire(models.Model):
    article = models.ForeignKey(Article, on_delete=models.CASCADE, related_name='commentaires')
    auteur = models.ForeignKey(User, on_delete=models.CASCADE, null=True, blank=True)
    texte = models.TextField()
    date_creation = models.DateTimeField(auto_now_add=True)
    approuve = models.BooleanField(default=False)
    
    class Meta:
        ordering = ['date_creation']
    
    def __str__(self):
        return f"Commentaire par {self.auteur.username if self.auteur else 'Anonyme'} sur {self.article.titre}"
```

```python
from django.shortcuts import render, redirect, get_object_or_404

from .models import Article, Categorie, Tag
from .forms import ArticleForm, CommentaireForm

class ArticleListView(ListView):
    model = Article
    template_name = 'articles/list.html'
    context_object_name = 'articles'
    paginate_by = 10
    ordering = ['-date_creation']
    allow_empty = True
    
    def get_queryset(self):
        """Filtrer par statut par défaut"""
        return Article.objects.filter(statut='publie')
    
    def get_context_data(self, kwargs):
        context = super().get_context_data(kwargs)
        context['categories'] = Categorie.objects.all()
        context['total_articles'] = Article.objects.count()
        return context

class ArticleDetailView(DetailView):
    model = Article
    template_name = 'articles/detail.html'
    context_object_name = 'article'
    slug_field = 'slug'
    slug_url_kwarg = 'slug'
    
    def get_queryset(self):
        return Article.objects.filter(statut='publie')
    
    def get_context_data(self, kwargs):
        context = super().get_context_data(kwargs)
        context['commentaires'] = self.object.commentaires.filter(approuve=True).order_by('-date_creation')[:10]
        context['form_commentaire'] = CommentaireForm()
        return context

class ArticleCreateView(LoginRequiredMixin, SuccessMessageMixin, CreateView):
    model = Article
    form_class = ArticleForm
    template_name = 'articles/form.html'
    success_url = reverse_lazy('article_list')
    success_message = "Article créé avec succès!"
    
    def form_valid(self, form):
        form.instance.auteur = self.request.user
        return super().form_valid(form)

class ArticleUpdateView(LoginRequiredMixin, UserPassesTestMixin, UpdateView):
    model = Article
    form_class = ArticleForm
    template_name = 'articles/form.html'
    success_url = reverse_lazy('article_list')
    success_message = "Article mis à jour avec succès!"
    
    def test_func(self):
        article = self.get_object()
        return self.request.user == article.auteur
    
    def get_success_url(self):
        return reverse('article_detail', args=[self.object.id, self.object.slug])

class ArticleDeleteView(LoginRequiredMixin, UserPassesTestMixin, DeleteView):
    model = Article
    template_name = 'articles/confirm_delete.html'
    success_url = reverse_lazy('article_list')
    success_message = "Article supprimé avec succès!"
    
    def test_func(self):
        article = self.get_object()
        return self.request.user == article.auteur

def article_search(request):
    """Vue de recherche fonctionnelle"""
    query = request.GET.get('q', '')
    results = Article.objects.filter(statut='publie')
    
    if query:
        results = results.filter(
            Q(titre__icontains=query) |
            Q(contenu__icontains=query) |
            Q(categorie__nom__icontains=query)
        )
    
    return render(request, 'articles/search_results.html', {
        'query': query,
        'results': results,
        'count': results.count()
    })
```

```python
register = template.Library()

@register.filter
def calculer_total(queryset):
    """Calculer le total d'un champ numérique sur un queryset"""
    total = 0
    for objet in queryset:
        if hasattr(objet, 'prix'):
            total += objet.prix
    return total

@register.filter
def initial_capital(chaine):
    """Mettre la première lettre en majuscule"""
    if not chaine:
        return chaine
    return chaine[0].upper() + chaine[1:]
```

### Guide de migration Django

#### De Django 3.x vers Django 4.x

1. Mise à jour de Python : Python 3.8+ requis pour Django 4.x
2. Changements de API :
   - `django.utils.text.capfirst` a été déplacé
   - Certaines méthodes de modèle ont changé de signature
   - Les gestionnaires de base de données ont de nouvelles options
3. Mises à jour de dépendances :
   ```bash
   pip install --upgrade Django django-rest-framework
   ```
4. Tester vos migrations :
   ```bash
   python manage.py makemigrations
   python manage.py migrate
   ```
5. Vérifier la compatibilité des packages tiers :
   - Vérifiez que tous vos packages Django sont compatibles avec la nouvelle version
   - Mettez à jour les packages non compatibles ou trouvez des alternatives

#### De Django 2.x vers Django 3.x

1. Suppression de `django.utils.six` : Plus besoin de compatibilité Python 2
2. Nouvelle syntaxe de chemin d'URL : `path()` recommandé au lieu de `url()`
3. Champs de date/time : `DateTimeField` maintenant utilise `timezone.now` par défaut
4. Cache : Certains paramètres de cache ont changé
5. Migrations : Nouveau système de migration par défaut
