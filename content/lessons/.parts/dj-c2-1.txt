## Introduction : donner vie à vos pages

Dans le chapitre précédent, vous avez appris à modéliser vos données avec les modèles Django et à administrer vos objets facilement grâce à l'interface d'administration. Mais une application web ne se résume pas à une base de données : elle doit afficher des pages, réagir aux clics des utilisateurs, valider des formulaires et servir des images. C'est exactement le rôle des vues et des templates, les deux piliers que vous allez maîtriser dans ce chapitre.

Une vue Django est tout simplement une fonction Python — ou une classe — qui reçoit une requête HTTP et renvoie une réponse HTTP. Cette définition volontairement simple cache une grande puissance : entre l'arrivée de la requête et l'envoi de la réponse, vous pouvez interroger la base de données, vérifier les droits d'un utilisateur, calculer des statistiques, rediriger vers une autre page ou encore déclencher un e-mail. La réponse peut être du HTML généré à partir d'un template, un fichier téléchargé, un flux JSON pour une API ou un simple message de confirmation. Chaque page que vous visitez sur un site Django est produite par une vue que quelqu'un a écrite.

Les templates, de l'autre côté, sont des fichiers textuels contenant du HTML mélangé à une syntaxe propre à Django : des variables entourées de doubles accolades, des balises de contrôle comme les boucles et les conditions, et des filtres qui transforment une valeur avant de l'afficher. Cette séparation entre la logique métier, qui vit dans les vues, et la présentation, qui vit dans les templates, est une des grandes forces de Django. Elle permet à un développeur de se concentrer sur les données et à un designer de travailler sur la mise en page sans marcher sur les pieds l'un de l'autre.

Ce chapitre vous guide pas à pas à travers les mécanismes essentiels. Vous commencerez par les vues fonctionnelles, la façon la plus directe de comprendre le cycle requête-réponse. Vous découvrirez ensuite le système d'URL et l'outil `reverse` qui permet de générer des liens sans jamais coder en dur une adresse. Vous plongerez dans le langage des templates avec l'héritage, les inclusions et les fichiers statiques. Vous apprendrez à construire des formulaires robustes avec `forms.Form` et `forms.ModelForm`, à les valider et à les protéger contre les attaques CSRF. Vous terminerez par le framework de messages et la gestion des fichiers téléversés, deux besoins quotidiens de toute application sérieuse.

## Vues fonctionnelles : le cycle requête-réponse

Une vue fonctionnelle est une fonction Python qui accepte un premier argument `request` et qui retourne un objet `HttpResponse`. Le plus simple exemple d'application Django ressemble à ceci. Vous importez la classe `HttpResponse` depuis `django.http`, vous définissez une fonction nommée par exemple `bonjour`, et vous renvoyez un objet construit avec le texte à afficher. Dès que Django reçoit une requête correspondant à l'URL associée à cette fonction, il l'appelle et renvoie au navigateur le contenu de la réponse.

L'objet `request` est une mine d'informations. Il contient la méthode HTTP utilisée, l'adresse demandée, les en-têtes de la requête, les cookies, la session, et — si l'utilisateur est authentifié — un attribut `user` représentant son compte. Vous pouvez donc adapter le comportement de votre vue en fonction de la méthode : une requête `GET` affiche généralement un formulaire vide, tandis qu'une requête `POST` traite les données soumises par ce formulaire. Ce principe, appelé séparation des traitements selon le verbe HTTP, est au cœur du web.

L'objet `HttpResponse` accepte plusieurs options utiles. Vous pouvez lui passer un code de statut avec l'argument `statut` — par exemple 404 pour signifier qu'une ressource n'existe pas — ou des en-têtes personnalisés avec l'argument `headers`. Django fournit également des raccourcis spécialisés : `JsonResponse` pour produire du JSON, `FileResponse` pour envoyer un fichier, `HttpResponseRedirect` pour rediriger le navigateur vers une autre adresse. Chaque raccourci encapsule une logique fréquente pour vous éviter de réécrire le même code à chaque fois.

Une vue typique commence presque toujours par tester la méthode de la requête. Si c'est un `GET`, vous affichez le formulaire. Si c'est un `POST`, vous récupérez les données depuis `request.POST`, vous les validez, et vous redirigez l'utilisateur vers une page de confirmation. Cette structure conditionnelle, présente dans quasiment toutes les vues de traitement de formulaires, est un motif que vous reconnaîtrez instantanément après l'avoir écrit une ou deux fois.

Le fichier qui contient les vues s'appelle conventionnellement `views.py` et se trouve dans le dossier de votre application. Django n'impose pas de nommage strict : vous pouvez organiser vos vues dans plusieurs modules si votre application grandit. L'essentiel est que chaque vue ait un nom clair, une responsabilité unique, et une docstring expliquant ce qu'elle fait. Les vues trop longues sont un signal d'alerte : c'est généralement le signe qu'une partie de la logique peut être extraite dans un service ou un formulaire.

## Les vues basées sur les classes : une alternative structurée

À côté des vues fonctionnelles, Django propose des vues basées sur les classes. L'idée est de regrouper dans une classe les méthodes correspondant à chaque verbe HTTP : `get`, `post`, `put`, `delete`. Django appelle automatiquement la méthode correspondante à la requête reçue. Une classe qui hérite de `View` suffit pour commencer ; des classes plus spécialisées comme `ListView` ou `DetailView` fournissent un comportement encore plus riche pour les cas fréquents.

L'avantage principal des vues basées sur les classes est la réutilisation par héritage. Vous pouvez définir une classe mère contenant la logique commune — par exemple la vérification qu'un utilisateur est connecté — puis faire hériter vos vues concrètes de cette classe. Les mixins, qui sont de petites classes apportant un comportement particulier, se combinent comme des briques. Une vue peut ainsi hériter d'un mixin d'authentification, d'un mixin de permission et d'un mixin de pagination sans que aucune ligne ne soit dupliquée.

La différence entre une vue fonctionnelle et une vue basée sur les classes n'est pas une question de performance mais de style et d'organisation. Les vues fonctionnelles sont plus simples à lire pour un débutant, car le flux est linéaire. Les vues basées sur les classes demandent un peu plus de familiarité avec l'héritage et les classes, mais elles évitent la duplication dans les projets de taille moyenne. Une pratique courante consiste à utiliser des vues fonctionnelles pour les cas ponctuels et des classes pour les opérations répétitives sur les modèles.

Si vous débutez, commencez par écrire des vues fonctionnelles, car elles rendent le mécanisme de requête-réponse parfaitement visible. Passez aux classes quand vous remarquez que plusieurs vues partagent la même structure. Cette progression naturelle vous permet d'acquérir les deux compétences sans vous sentir perdu. De nombreuses bibliothèques tierces, comme celles qui proposent des API REST ou des tableaux de bord, fournissent déjà des vues basées sur les classes qu'il vous suffit d'étendre.

## Le système d'URL : du chemin à la vue

Pour qu'une vue soit accessible, il faut associer son adresse à sa fonction. Cette association se fait dans le fichier `urls.py` de votre application, que vous déclarez ensuite dans le fichier `urls.py` du projet. Le mécanisme est le suivant : Django parcourt la liste des motifs d'URL dans l'ordre, et dès qu'un motif correspond au chemin demandé, il appelle la vue associée et lui transmet la requête.

Un motif d'URL se définit avec la fonction `path`, qui prend en argument la chaîne de motif, la vue à appeler, et un nom optionnel. Les deux points sont séparés par des barres obliques, conformément aux conventions web. Un motif tel que `articles/` correspondra à l'adresse se terminant par `articles/`. Le nom du motif est indispensable : il vous permet de référencer cette URL depuis le code ou les templates sans jamais écrire l'adresse en dur.

Les convertisseurs de chemin permettent de capturer des portions de l'URL et de les passer à la vue sous forme d'arguments. Le convertisseur pour entier capture un nombre et le nomme selon votre choix, tandis que le convertisseur pour chaîne capture une séquence sans barre oblique. Vous pouvez également définir des convertisseurs personnalisés en écrivant une petite classe avec une expression régulière et une méthode de conversion. Cette fonctionnalité est précieuse pour créer des URL propres, dites « SEO friendly », comme `/articles/2026/mon-premier-article/`.

La fonction `reverse` est l'outil qui transforme un nom d'URL en adresse réelle. Au lieu d'écrire `/articles/5/` en dur, vous appelez `reverse('article-detail', args=[5])`, et Django calcule l'adresse à partir de la configuration. Si vous modifiez plus tard le motif d'URL, tous vos liens restent valides. Dans les templates, la balise `url` joue le même rôle. Cette discipline, qui consiste à ne jamais coder les URL en clair, évite une multitude de liens cassés lors des refontes du site.

Un projet Django contient généralement un fichier `urls.py` à la racine du projet et un fichier par application. Le fichier racine se contente d'inclure les fichiers des applications avec `include`. Cette organisation modulaire permet à chaque application d'être autonome et réutilisable dans un autre projet. Quand vous créez une nouvelle application, n'oubliez jamais d'ajouter son `urls.py` à la racine, sinon ses vues resteront inaccessibles.

## À retenir

Le mécanisme fondamental de Django repose sur un échange simple : le navigateur envoie une requête, Django identifie la vue correspondant à l'URL demandée, la vue traite la requête et renvoie une réponse que le navigateur affiche. Une vue fonctionnelle est une fonction qui reçoit un objet `request` et retourne un objet `HttpResponse`. Les vues basées sur les classes offrent une alternative structurée, fondée sur l'héritage et les mixins, particulièrement adaptée aux opérations répétitives sur les modèles.

L'objet `request` contient tout le contexte de la requête : méthode, en-têtes, session, utilisateur. L'objet `HttpResponse` accepte un contenu, un code de statut et des en-têtes. Les raccourcis comme `JsonResponse`, `FileResponse` et `HttpResponseRedirect` simplifient les cas courants. Les vues fonctionnelles sont plus linéaires et plus accessibles aux débutants ; les vues basées sur les classes favorisent la réutilisation du code.

Le système d'URL associe une adresse à une vue grâce à la fonction `path`. Les convertisseurs de chemin capturent des portions de l'URL et les transmettent à la vue. La fonction `reverse` et la balise `url` génèrent des adresses à partir du nom du motif, ce qui préserve la cohérence du site lorsque les URL évoluent. Un projet bien organisé déclare les URLs de chaque application dans un fichier propre, inclus par le fichier racine.
