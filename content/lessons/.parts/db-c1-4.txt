Vous voici au terme de la partie conceptuelle du parcours bases de données. Les trois leçons qui précèdent vous ont conduits du vocabulaire du modèle relationnel jusqu'au schéma normalisé d'une bibliothèque complète. Cette dernière page rassemble l'essentiel, liste les pièges les plus fréquents, propose des pistes d'approfondissement et vous envoie vers l'exercice pratique qui conclut le chapitre. Prenez le temps de relire les points de synthèse : la consolidation active, c'est-à-dire reformuler chaque idée avec vos propres mots, vaut mieux qu'une relecture passive.

Le schéma ci-dessous résume le modèle atteint à l'issue de la normalisation. Sept tables, des clés primaires simples, des clés étrangères explicites, aucune redondance superflue. Recopiez-le dans votre outil de requête, chargez quelques lignes de test, puis écrivez une requête qui affiche, pour chaque emprunt en cours, le nom du lecteur, le titre de l'ouvrage et la cote de l'exemplaire. Si vous y parvenez sans hésiter, les objectifs de ce chapitre sont atteints, et vous êtes prêt pour la suite du parcours.

```sql
CREATE TABLE villes (
  identifiant INTEGER PRIMARY KEY,
  nom         TEXT NOT NULL UNIQUE,
  code_postal TEXT NOT NULL
);

CREATE TABLE lecteurs (
  identifiant      INTEGER PRIMARY KEY,
  nom              TEXT NOT NULL,
  prenom           TEXT NOT NULL,
  courriel         TEXT NOT NULL UNIQUE,
  ville_id         INTEGER NOT NULL REFERENCES villes (identifiant),
  date_inscription DATE NOT NULL
);

CREATE TABLE ouvrages (
  identifiant INTEGER PRIMARY KEY,
  titre       TEXT NOT NULL,
  auteur      TEXT NOT NULL,
  isbn        TEXT UNIQUE
);

CREATE TABLE exemplaires (
  identifiant INTEGER PRIMARY KEY,
  ouvrage_id  INTEGER NOT NULL REFERENCES ouvrages (identifiant),
  cote        TEXT NOT NULL UNIQUE,
  etat        TEXT NOT NULL
);

CREATE TABLE emprunts (
  identifiant  INTEGER PRIMARY KEY,
  lecteur_id   INTEGER NOT NULL REFERENCES lecteurs (identifiant),
  date_sortie  DATE NOT NULL,
  date_retour  DATE
);

CREATE TABLE emprunt_exemplaires (
  emprunt_id    INTEGER NOT NULL REFERENCES emprunts (identifiant),
  exemplaire_id INTEGER NOT NULL REFERENCES exemplaires (identifiant),
  etat_retour   TEXT,
  PRIMARY KEY (emprunt_id, exemplaire_id)
);

CREATE TABLE reservations (
  identifiant   INTEGER PRIMARY KEY,
  lecteur_id    INTEGER NOT NULL REFERENCES lecteurs (identifiant),
  ouvrage_id    INTEGER NOT NULL REFERENCES ouvrages (identifiant),
  date_demande  DATE NOT NULL,
  position      INTEGER NOT NULL
);
```

Avant d'entrer dans la liste des points de retenir, rappelons la démarche qui a guidé tout le chapitre. On a commencé par le domaine métier, une bibliothèque avec ses lecteurs, ses ouvrages et ses emprunts. On a traduit ce domaine en entités, attributs et relations, sans se préoccuper de la technique. On a dessiné un diagramme, discuté des cardinalités, vérifié les bornes minimales et maximales. On a ensuite projeté ce diagramme en tables SQL, avec des clés primaires, des clés étrangères et des contraintes d'unicité. Enfin, on a normalisé le résultat pour supprimer les redondances. Cette démarche, du conceptuel au logique, du logique au normalisé, est celle que vous retrouverez dans chaque projet professionnel, quelle que soit la taille de l'équipe ou le domaine d'activité.

## À retenir

- Une base de données relationnelle organise les données en tables, colonnes typées et lignes uniques, liées entre elles par des clés.
- Une entité devient une table, un attribut devient une colonne, un enregistrement devient une ligne ; ne confondez pas ces trois niveaux.
- La clé primaire identifie chaque ligne sans ambiguïté ; elle combine obligation et unicité, et elle doit rester stable dans le temps.
- La clé étrangère référence la clé primaire d'une autre table et garantit l'intégrité référentielle, y compris à la suppression.
- Les cardinalités se lisent dans les deux sens ; une relation plusieurs-à-plusieurs se dédouble en table intermédiaire.
- Le diagramme entité-association se dessine avant d'écrire le code SQL, et sert de support à la validation métier.
- La normalisation élimine les redondances : la première forme traite les valeurs non atomiques, la deuxième les dépendances partielles, la troisième les dépendances transitives.
- Une table saine possède une clé primaire simple, des valeurs atomiques et aucun attribut non clé dépendant d'une partie de la clé ou d'un autre attribut non clé.

## Erreurs fréquentes

L'erreur la plus répandue chez les débutants consiste à confondre entité, attribut et enregistrement. On voit des colonnes prénommées comme des entités, ou des tables créées pour héberger une seule propriété. Reprenez le test simple : si vous pouvez compter les occurrences et leur donner un nom commun, c'est une entité ; si c'est une propriété mesurable qui prend une valeur par enregistrement, c'est un attribut. Ce réflexe de classement, répété sur quelques dizaines de cas, fixe le vocabulaire définitivement et évite les schémas incohérents dont personne ne sait plus, deux ans après, ce que chaque table représente réellement.

La seconde erreur consiste à utiliser comme clé primaire une information métier susceptible de changer. Un courriel, un numéro de téléphone, un libellé de ville : tout cela peut se modifier, tout cela peut se réutiliser après un changement de propriétaire. Quand la clé change, toutes les références doivent changer en même temps, opération coûteuse et risquée. Préférez un identifiant technique stable, et contraints en unicité les attributs naturels qui doivent le rester. La clé technique est un détail d'implémentation, pas une information à afficher, et la distinguer de la clé d'affichage est le signe d'une conception mûre.

La troisième erreur est d'oublier les clés étrangères, ou de les déclarer sans politique de suppression adaptée. Sans contrainte, la base accepte n'importe quoi, et les incohérences s'accumulent en silence jusqu'au jour où un rapport les révèle. Avec une politique cascade mal choisie, on supprime au passage un historique qu'on croyait précieux. Discutez ces choix avec le métier, écrivez-les dans la contrainte, et laissez le moteur faire respecter la décision. L'intégrité référentielle n'est pas une option de confort : c'est la garantie que vos jointures racontent toujours une histoire vraie.

Une quatrième erreur concerne les cardinalités, et particulièrement leur sens de lecture. Dire « un emprunt, plusieurs lecteurs » inverse la réalité et produit, si l'on applique la règle de placement des clés étrangères à l'envers, un schéma impossible à alimenter. Reformulez toujours les deux sens à voix haute avant de dessiner : d'un côté un lecteur a zéro, un ou plusieurs emprunts ; de l'autre un emprunt appartient à un seul lecteur. Cette minute de vérification économise des heures de correction, et elle rend les revues de conception beaucoup plus fluides, puisque chacun parle de la même relation avec les mêmes mots.

Enfin, nombreux sont ceux qui croient la normalisation synonyme de suppression de doublons de lignes. Elle ne s'attaque pas seulement aux lignes identiques : elle traque les informations recopiées à l'intérieur de lignes distinctes, dépendances partielles et transitives comprises. Une table peut ne contenir aucune ligne strictement identique et rester profondément mal normalisée. Posez-vous toujours la question de la direction des dépendances, et non de l'apparence des données. Un schéma qui passe les trois formes normales est un schéma dont chaque colonne dépend clairement, et uniquement, de la clé primaire de sa propre table.

## Pour aller plus loin

Pour consolider ces acquis par la pratique, rien ne remplace la répétition dans un environnement réel. Installez SQLite ou PostgreSQL sur votre machine, recopiez le schéma de synthèse, chargez environ trente lecteurs et cent emprunts, puis écrivez les requêtes les plus simples possible : les emprunts en retard, les lecteurs sans emprunt depuis un an, le top des ouvrages empruntés. Chaque requête vous forcera à reprendre une jointure, donc à revoir une clé étrangère, donc à ancrer la mécanique relationnelle dans le geste, et pas seulement dans la mémoire visuelle.

Les documentations officielles des moteurs comportent des chapitres de tutoriel d'excellente facture, et les cours en ligne généralistes proposent des parcours interactifs dédiés au SQL. Cherchez en priorité des ressources qui font écrire du code dans le navigateur : le geste de formuler une requête, de la voir échouer, de la corriger, est le vrai moteur d'apprentissage. Complétez par quelques exercices de modélisation pure, sans machine, où l'on vous donne un cahier des charges en français et où l'on attend un diagramme : c'est ainsi que l'on développe l'œil du concepteur, celui qui voit les cardinalités dans une phrase et les dépendances dans une colonne.

Les outils de dessin de diagrammes, les formats texte de description de schémas et les générateurs automatiques de documentation sauront vous servir dès le premier projet professionnel. Prenez l'habitude de versionner le schéma à côté du code applicatif, et de faire relire vos modèles par un collègue avant la première migration en production. Enfin, lorsque vous vous sentirez à l'aise avec la troisième forme normalisée, abordez les thèmes voisins : les index pour la performance, les transactions pour la cohérence concurrente, et les stratégies de migration qui permettent de faire évoluer un schéma en production sans interruption de service. Ces sujets font l'objet des chapitres suivants du parcours.

L'exercice de fin de chapitre vous demande de concevoir et d'implémenter le schéma complet de la bibliothèque, à partir du cahier des charges fourni dans la fiche de pratique. Vous y créerez les tables, les clés primaires, les clés étrangères et les contraintes d'unicité, puis vous chargerez des données d'exemple et vous écrirez les requêtes de restitution attendues. Traitez-le comme un vrai projet : commencez par le diagramme sur papier, vérifiez chaque cardinalité à voix haute, transformez-le en commandes SQL, et n'allez de l'avant que lorsque chaque contrainte est en place. L'objectif n'est pas de produire le script le plus élégant, mais d'éprouver chaque règle apprise dans les conditions réelles du développement.

Si vous bloquez, revenez aux sections de synthèse, puis reprenez l'exemple guidé du deuxième chapitre, qui construisait le même schéma étape par étape. L'important est de ressentir la logique : atomicité des valeurs, stabilité des clés, intégrité référentielle, séparation des dépendances. Une fois votre script validé et vos requêtes exécutées, poursuivez avec le chapitre suivant, qui vous apprendra à interroger ces tables avec puissance : filtres, agrégations, jointures multiples et sous-requêtes. Le terrain de jeu est en place ; il ne reste plus qu'à jouer. Prenez le temps de bien jouer, c'est-à-dire de comprendre chaque message d'erreur, de corriger chaque hypothèse, et de repartir avec des réflexes que vous appliquerez sans y penser dès votre prochain projet.
