## Le langage des templates : variables et filtres

Le langage de template de Django a été conçu pour rester simple tout en étant expressif. Une variable s'affiche en l'entourant de doubles accolades : `{{ nom }}`. La variable est résolue dans le contexte passé à la template par la vue : si vous transmettez un dictionnaire `{'nom': 'Alice'}`, la chaîne `{{ nom }}` est remplacée par « Alice ». Si la variable est un objet, vous accédez à ses attributs avec le point : `{{ article.titre }}`. Les indices de liste fonctionnent de la même manière : `{{ articles.0.titre }}`.

Les filtres modifient l'affichage d'une variable sans toucher à la valeur d'origine. Le filtre `date` formate une date selon un modèle donné, `lower` convertit en minuscules, `truncatechars` coupe un texte à un certain nombre de caractères avec des points de suspension. Les filtres s'enchaînent avec le caractère barre verticale : `{{ article.contenu|truncatechars:200|linebreaksbr }}`. Cette chaîne de filtres, lue de gauche à droite, transforme progressivement la valeur brute en sa version finale prête à être affichée.

Le filtre `default` remplace une valeur vide par un texte de substitution, ce qui est utile pour les champs optionnels. Le filtre `length` renvoie la taille d'une liste ou d'une chaîne. Le filtre `escape` convertit les caractères spéciaux en entités HTML, ce qui est un premier rempart contre les failles d'injection — bien que Django échappe automatiquement les variables par défaut, ce qui vous protège déjà sans effort. Connaître une dizaine de filtres courants vous permet de couvrir la grande majorité des besoins d'affichage.

Un point important concerne les valeurs manquantes. Par défaut, Django affiche une chaîne vide quand une variable n'existe pas dans le contexte, au lieu de déclencher une erreur. Ce comportement tolérant facilite le développement, mais il peut masquer une erreur de nommage. Si vous préférez être alerté, vous pouvez configurer le moteur de templates pour qu'il lève une exception en cas de variable inconnue. En production, la valeur par défaut, silencieuse, est généralement préférable pour ne pas afficher une page blanche à l'utilisateur.

Les variables peuvent être des objets complexes : modèles, dictionnaires, listes, voire fonctions. Django suit une résolution en plusieurs étapes : il essaie d'abord la clé du dictionnaire, puis l'attribut de l'objet, puis l'indice de la liste. Cette flexibilité permet d'utiliser la même syntaxe dans des contextes variés. Si un objet ne possède pas l'attribut demandé, le résultat est simplement vide, sauf si la levée d'erreurs est activée.

## Les tags de contrôle : conditions et boucles

Les tags de contrôle ajoutent une logique conditionnelle et itérative à vos templates. Le tag `if` permet d'afficher du contenu seulement si une condition est remplie. Vous pouvez comparer des valeurs, tester l'existence d'une variable, combiner des conditions avec `and`, `or` et `not`. Le bloc se termine par `endif`, une obligation qui structure le code et le rend lisible. Les conditions sont évaluées dans le contexte du template, ce qui permet d'adapter l'affichage sans alourdir la vue.

La boucle `for` parcourt une liste et répète un bloc pour chaque élément. Une variable spéciale `forloop` donne accès au compteur, à l'index, à une indication de premier et dernier élément. Cette variable est pratique pour alterner les couleurs des lignes d'un tableau ou afficher un séparateur entre les éléments. La boucle peut également tester si la liste est vide avec le mot-clé `empty`, évitant ainsi d'afficher un tableau sans contenu.

Les tags de commentaire permettent d'annotations dans le template sans qu'elles n'apparaissent dans le HTML final. Le tag `comment` délimite un bloc ignoré par le moteur de templates, tandis que la syntaxe avec accolades et dièses sert pour une ligne unique. Cette distinction est utile : le commentaire en ligne est pratique pour une note rapide, tandis que le bloc de commentaire est plus lisible pour documenter une section entière.

Un tag très utilisé est `url`, déjà mentionné, qui génère une adresse à partir du nom d'un motif. Le tag `csrf_token` insère un jeton de sécurité caché dans les formulaires, un mécanisme indispensable que nous détaillerons plus loin. Le tag `with` permet de définir une variable locale dans le template, ce qui évite de répéter une expression longue plusieurs fois dans le même bloc. Ces tags, par leur simplicité, couvrent l'immense majorité des besoins de présentation.

Les filtres et tags peuvent sembler limités par rapport à un langage de programmation complet, et c'est volontaire. Django encourage à garder les templates simples et à placer la logique métier dans les vues ou les modèles. Si vous vous apercevez que vos templates contiennent des calculs complexes ou des requêtes de base de données, c'est le signe que cette logique doit être déplacée ailleurs — par exemple dans une méthode du modèle ou une fonction utilitaire appelée par la vue.

## L'héritage et les inclusions de templates

L'héritage de templates est le mécanisme qui vous permet d'éviter de répéter la structure HTML de chaque page. Vous créez un template de base, souvent appelé `base.html`, qui contient le squelette commun : la déclaration `DOCTYPE`, l'en-tête, la barre de navigation, le pied de page. Dans ce squelette, vous placez des blocs nommés avec `{% block contenu %}{% endblock %}`. Les templates enfants héritent du template parent et remplissent ces blocs avec leur contenu propre.

Pour hériter d'un template, le template enfant commence par une balise `{% extends "base.html" %}`. Toute la partie commune est automatiquement reprise du parent. Si vous ne redéfinissez pas un bloc, le contenu par défaut du parent est utilisé. Cette architecture en couches — un parent général, un template intermédiaire pour une section, un template final pour une page — permet une organisation claire et évolutive.

Les inclusions vont plus loin en permettant d'insérer un fragment de template dans un autre. La balise `{% include "menu.html" %}` charge le fichier spécifié et l'insère à l'emplacement voulu. Cette technique est idéale pour les composants réutilisables : une carte d'article, un formulaire de connexion, un bloc de pagination. Vous pouvez passer des variables au template inclus en les définissant avec `with` avant l'inclusion.

Les fichiers de templates se stockennt conventionnellement dans un dossier `templates` à l'intérieur de chaque application. Django les cherche automatiquement dans toutes les applications installées. Pour éviter les conflits de noms — deux applications pourraient avoir un `detail.html` — il est recommandé de créer un sous-dossier portant le nom de l'application, comme `templates/blog/detail.html`. Cette précaution devient indispensable dès que le projet compte plusieurs applications.

L'ordre de recherche des templates suit l'ordre des applications dans `INSTALLED_APPS`. Si deux applications possèdent un template du même nom, le premier trouvé est utilisé. C'est pourquoi les templates du projet global, stockés dans un dossier défini dans la configuration, sont souvent placés en priorité. Cette souplesse permet de surcharger un template d'une application tierce sans modifier le code de l'application, une fonctionnalité précieuse pour la maintenance.

```html
{% extends "base.html" %}

{% block contenu %}
  <h1>{{ article.titre }}</h1>
  <p class="date">Publié le {{ article.date_publication|date:"d F Y" }}</p>
  <div class="contenu">
    {{ article.contenu|linebreaks }}
  </div>
  <p><a href="{% url "article-liste" %}">Retour à la liste</a></p>
{% endblock %}
```

Ce fragment montre un template enfant typique : il hérite d'un parent, remplit le bloc `contenu` avec des variables, des filtres et un lien généré par la balise `url`. La lisibilité est un objectif premier : un template bien structuré se comprend sans avoir besoin de lire le code Python qui l'accompagne.

## Les fichiers statiques : images, styles et scripts

Les fichiers statiques — feuilles de style CSS, images, fichiers JavaScript, polices — sont des ressources qui ne changent pas à chaque requête. Django les sert en développement grâce à l'application `staticfiles`, et les configure pour la production avec un service de stockage adapté. La variable `STATIC_URL` définit l'adresse de base, tandis que `STATICFILES_DIRS` liste les dossiers où chercher les fichiers pendant le développement.

Dans un template, vous chargez un fichier statique avec la balise `{% load static %}` en tête, puis `{% static "css/style.css" %}`. Cette balise génère l'adresse complète, en tenant compte de la configuration et des éventuels mécanismes de hachage pour éviter les problèmes de cache. Pour les images, le même mécanisme s'applique : `{% static "images/logo.png" %}`.

En production, la commande `collectstatic` rassemble tous les fichiers statiques des applications et du projet dans un dossier unique défini par `STATIC_ROOT`. Ces fichiers peuvent ensuite être servis par un serveur web performant ou un stockage objet comme Amazon S3. Cette étape est indispensable : le serveur de développement n'est pas conçu pour servir un trafic réel, et les fichiers statiques doivent être livrés de manière optimale.

Les médias, c'est-à-dire les fichiers téléversés par les utilisateurs, suivent une logique différente. Ils sont stockés dans le dossier défini par `MEDIA_ROOT` et servis à l'adresse de base `MEDIA_URL`. En production, vous configurez votre serveur web pour servir ce dossier, ou vous utilisez un stockage distant. La distinction entre fichiers statiques du code et fichiers téléversés par les utilisateurs est fondamentale : les premiers sont gérés par les développeurs, les seconds par les utilisateurs.

```python
# settings.py
STATIC_URL = "/static/"
STATICFILES_DIRS = [BASE_DIR / "static"]
STATIC_ROOT = BASE_DIR / "staticfiles"

MEDIA_URL = "/media/"
MEDIA_ROOT = BASE_DIR / "media"
```

Cette configuration, typique d'un projet Django, sépare clairement les fichiers des développeurs des fichiers des utilisateurs. Les chemins sont construits avec `BASE_DIR` pour rester indépendants du répertoire d'installation. Vous remarquerez que la configuration est minimaliste : c'est tout ce dont Django a besoin pour gérer ces fichiers de manière cohérente.

## À retenir

Le langage de template de Django s'articule autour des variables `{{ }}` et des filtres `|` qui transforment l'affichage sans modifier les données. Les tags de contrôle `if`, `for`, `url`, `csrf_token` et `with` ajoutent une logique de présentation. L'héritage avec `extends` et `block` permet de structurer les pages en couches, tandis que `include` insère des fragments réutilisables. Les fichiers statiques sont servis avec `{% static %}` et rassemblés par `collectstatic` en production. Les fichiers téléversés par les utilisateurs sont gérés par la configuration `MEDIA_URL` et `MEDIA_ROOT`.

La résolution des variables suit une recherche en plusieurs étapes : clé de dictionnaire, attribut d'objet, indice de liste. Une variable manquante produit une chaîne vide par défaut, ce qui facilite le développement mais peut masquer une erreur de nommage. Les filtres courants `date`, `lower`, `truncatechars`, `default` et `length` couvrent la majorité des besoins d'affichage. La balise `url` génère une adresse à partir d'un nom de motif, préservant la cohérence du site.

Les templates doivent rester simples : la logique complexe appartient aux vues ou aux modèles. L'ordre de recherche des templates suit `INSTALLED_APPS`, d'où l'utilité des sous-dossiers nommés d'après l'application. En production, les fichiers statiques sont servis par un service distinct du serveur Django, et les médias suivent une configuration dédiée. Ces principes garantissent des templates lisibles, maintenables et performants.
